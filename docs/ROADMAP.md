# Mandaryn 开发路线图（ROADMAP）

> **用途**：记录 Mandaryn 的开发计划与完成情况。每一项都是一个可独立验收的开发目标，
> 只描述「做什么、达成什么效果」，不绑定交付时间。
>
> **与需求文档的关系**：本文件是**开发视角的推进清单**，需求编号（`FR-xx`/`NFR-xx`）、
> 验收标准与状态机定义仍以 [PRD.md](./PRD.md)、[ARCHITECTURE.md](./ARCHITECTURE.md) 为准；
> 二者冲突时以需求文档为准，并回来修正本文件。
>
> **变更历史**：见 [CHANGELOG.md](./CHANGELOG.md)。

## 标记含义

| 标记 | 含义 |
|------|------|
| `[x]` | 已完成：目标达成，可用并有对应验证手段 |
| `[~]` | 未完成：已有部分代码或文档产出，但目标尚未达成 |
| `[ ]` | 未开始：尚无实现 |

> 阶段标题上的标记是该阶段的**汇总结论**：全部条目 `[x]` 才标 `[x]`，有任一条目未完成则为 `[~]`，
> 全部条目都未开始才标 `[ ]`。因此阶段标 `[~]` 时，其下仍可能有已完成的条目。

## 0. 工程底座与外壳 `[~]`

### 0.1 应用外壳与窗口

- [x] **Wails v3 应用骨架**：`main.go` 仅做 `embed.FS` + `app.Run`，业务装配集中在 `internal/app`，业务代码不回流入口文件。
- [x] **分平台窗口配置**：Windows / Linux 无边框由前端自绘标题栏，macOS 保留原生红绿灯并垂直居中；平台差异走 `window_<os>.go` 的 build tag，不在业务里判断 `runtime.GOOS`。
- [x] **自绘标题栏**：`TitleBar` 提供 `leading` / `center` 插槽，高度统一由 `--fd-titlebar-h` 驱动，与内容区网格对齐。
- [x] **子窗口系统**：`ChildWindowService` 支持 `confirm` / `message` / `blank` 预设，子窗口与主窗口共享主题与语言。
- [x] **系统托盘**：开关持久化、托盘面板（失焦 / Esc 隐藏）、菜单文案走 i18n、面板可驱动主窗口路由。

### 0.2 前端架构

- [x] **MVVM 规范落地**：每页面 / 组件独立目录，View / ViewModel / Style 三件分离；View 与 ViewModel 均不直接 import bindings。
- [x] **布局预设系统**：9 种内置预设（图标栏 / 展开侧栏 / 顶部导航 / 融合标题栏 / 右侧栏 / 底部 Dock / 悬浮 Dock / 浮动卡片 / 专注），CSS Grid 外壳按 `data-placement` / `data-frame` 切换，支持注册自定义预设，选择持久化到 SQLite。
- [x] **悬浮 Dock 拖拽**：指针捕获拖动手柄，夹取在内容区内不进标题栏，双击复位，位置持久化。
- [x] **主题系统**：调色板编译为 `--fd-*` CSS 变量 + Mantine 主色阶，3 套内置预设 + 自定义调色板 + 跟随系统；组件样式只用 CSS Modules 与语义变量。
- [x] **i18n**：`zh-CN`（默认）/ `en-US`，公用文案与页面级文案分离，运行时切换，主窗口 / 子窗口 / 托盘面板实时同步。
- [x] **启动就绪与骨架屏**：`index.html` 内联骨架消除白屏，偏好读回后发就绪信号再淡出，避免布局跳变。
- [x] **路由与参数**：路由表为唯一事实源，`navigate(id, params)` 支持带参跳转，页面骨架独立 chunk 按需加载。
- [x] **x-pro 组件库**：DataGrid Pro / Premium（列菜单 / 列宽拖拽 / 列钉住 / 行钉住 / 树形 / 主从 / 分组聚合 / 范围选择）与 8 种高级图表。

### 0.3 后端分层与工具层

- [x] **后端分层**：`internal/app`（装配）+ `internal/services`（薄壳）+ `internal/events`（事件契约）+ `internal/utils`（工具）。
- [x] **工具层五项**：`httpx`（代理感知 HTTP）、`procx`（子进程 + JobObject / pgid 托管）、`cryptox`（AES-GCM）、`logx`（slog + rotate）、`filex`（原子写）。
- [x] **事件集中注册**：事件名统一注册，前后端共享同一契约来源。
- [x] **子进程白名单服务**：前端只能调用注册过的命令并通过参数模式校验，不开放万能命令执行。
- [x] **导出服务**：CSV（带 BOM）/ XLSX（真 `.xlsx`）落盘，经原生「另存为」对话框，前端不再自行拼文件。

### 0.4 持久化底座

- [x] **SQLite + GORM 接入**：纯 Go 驱动、WAL / `busy_timeout` / `mmap_size` 等 PRAGMA 调优、单连接池。
- [x] **AutoMigrate 注册中心**：加表只需追加模型到 `AllModels`，重启自动建表 / 加列 / 加索引，零迁移文件。
- [x] **偏好与设置两表**：`preferences`（开放 KV）+ `app_settings`（单行设置），前端 Provider 全异步化，无 `localStorage`。
- [x] **数据目录切换**：`storagesvc` 原子替换 DB 句柄，业务服务始终取活跃句柄；切换后密钥 / 日志与库同根，避免会话丢失。
- [x] **表统计与清理**：按表字节 / 行数统计并可逐表清空（带原生确认），支撑设置页「数据存储」。
- [x] **业务表落地**：`sessions` / `segments` / `speakers` / `session_speakers` / `roles` / `bundles` / `downloads` / `session_events` / `data_migrations` / `outbound_log` 十张表的模型与索引。（十张表已全部注册进 `AllModels` 并随 AutoMigrate 建表；`Clearable` 按「清空是否会不可恢复地丢用户数据」区分 —— `sessions` / `segments` / `speakers` 一律 `false`，删除必须走业务动作。此前该勾选框漏更新，Wave B 已交付）

## 3. `FR-02` 应用级音频捕获 `[~]`

- [x] **捕获抽象与能力矩阵**：定义统一的源枚举与捕获接口，按平台声明能力（进程树捕获 / 设备回环），上层只依赖能力而不依赖平台。
- [ ] **Windows 进程树捕获**：只抓指定进程及其子进程树的输出混音，不混入其他应用声音。（`go-wca` 未暴露 `ActivateAudioInterfaceAsync`，且本机 Build 19045 < 20348 不可验证；已诚实声明能力为 false，见 `DEV-ISSUES-S1.md` S1-07）
- [ ] **macOS 进程音频捕获**：基于系统原生进程音频采集能力实现同语义捕获，并处理权限请求与拒绝路径。（平台桩已就位，返回 `ERR_CAPTURE_UNAVAILABLE` 与平台前提说明）
- [ ] **Linux PipeWire 捕获**：按节点抓取目标应用音频，无 PipeWire 时降级到监视源。（同上，平台桩已就位）
- [x] **设备回环降级**：平台不支持进程级捕获时自动降级为设备回环，并在界面明确标注「会包含所有应用声音」。
- [x] **异常检测与恢复**：目标应用退出、输出设备切换、设备拔出分别有重连 / 迁移 / 暂停恢复路径，且会话不因设备抖动而丢失。（2s 轮询监视 + `Channel.Err()` + `ProbeSource` 按进程树区分「未运行/运行但无声」）
- [x] **捕获服务薄壳与事件**：`capturesvc` 暴露源列表与可用性变化，前端能实时看到应用启动 / 退出、设备增减。
- [x] **源选择界面**：录制页展示可选源、运行状态与子进程数，未运行的源置灰并给出刷新与替代方案。

## 4. `FR-03` 录制与转写时机 `[~]`

### 4.1 采集与落盘

- [x] **音频管线**：源格式重采样并混为单声道，进入固定格式环形缓冲，为落盘与后续推理提供稳定输入。
- [x] **音频落盘**：按会话写入音频文件，时间基用帧计数换算（不用墙钟），保证休眠与设备时钟漂移下的时间轴正确。
- [x] **采集指标**：采集期间发布电平、已录时长与已写字节，前端实时可见且不阻塞主线程。
- [x] **无音频输入处理**：电平长时间为零时提示「未检测到音频」并引导排查，不静默失败、不产生空录音实例。

### 4.2 状态机与录音实例

- [x] **录制状态机**：实现 `idle` → `preparing` → `recording` ↔ `paused` → `finalizing` → `completed` / `interrupted` / `failed`，非法转换被拒绝并记录错误码。
- [x] **录音实例封存**：停止录制时封口音频文件并写入元数据（源、起止、时长、采样格式、字节数），使录音立即可回放、可被转写。
- [x] **收尾快速返回**：收尾阶段只做封存，不同步跑推理，避免拖慢收尾放大崩溃丢音频的风险。
- [x] **崩溃与断电恢复**：重启自检发现未正常结束的会话时修补音频并标记中断，音频与已产出片段可回放，可稍后转写或重转。
- [x] **录制服务薄壳**：`recordingsvc` 提供启停 / 暂停 / 恢复 / 状态查询 / 崩溃恢复，只做类型转换与事件转发。

### 4.3 延后转写任务

- [x] **转写状态轴**：以独立状态（未转写 / 排队 / 转写中 / 完成 / 失败）表达转写进度，与录制主状态正交，不扩展主状态枚举。
- [x] **转写任务执行**：对已存录音实例读取音频、分句、逐句离线转写并落片段，支持取消、重转与幂等覆盖。
- [x] **进度与断点续跑**：记录已转写位置，任务被抢占或中断后可从断点继续，已完成句子不重复处理。
- [x] **触发时机**：支持用户手动发起立即执行，以及整机空闲时自动排队执行；被前台占用抢占时让位并保留进度。（手动发起、让位、整机空闲判定与「只拦空闲任务、手动恒放行」均已实现并接线：`perf.Service.IdleFor` → `transcribe.Options.IdleFor` → `Scheduler.pick`）
- [x] **转写服务与事件**：`transcriptsvc` 暴露发起 / 取消 / 查询与状态事件，前端可展示进度与失败原因。
- [x] **边录边转开关**：提供可选开关（默认关闭），开启后在录制中实时出字并按句定稿；该路径的时延指标才适用。（**全链路已真机跑通**：`recording.LiveSink` 非阻塞旁路（有界队列，满则丢弃推理样本、绝不阻塞落盘）+ `transcribe.LiveRunner`（VAD 定稿、`(session_id,seq)` 与延后转写同规则）+ `asr.StreamingEngine` 可选能力 + `asrlocal` 的 sherpa `OnlineRecognizer` 实现（transducer 三件套）+ `RouterOptions.Streaming`/`StreamingProbe` 装配 + `app_settings.live_transcribe`（默认 false，录制中双向拒绝切换）+ `LiveAvailability`（API-4.8）+ 设置页开关与录制页实时字区。关闭时行为与未实现前**逐字一致**（`LiveEnabled`/`NewLiveSink` 为 nil 即零开销，有测试守护）；开启后 `Stop` 不再自动整段转写（避免重复推理），手动重转仍幂等。**真机实测**（官方 zipformer-zh-streaming + 真实中文语音）：加载 993ms，5.59s 音频累积 7 条增量 → `"开放时间早上九点至下午五点"`，`Reset` 后两轮逐字一致无重复，与离线 SenseVoice 结果相似度 0.71（近音字 + ITN 差异，正是两遍法要补的差距）。**注意**：时延指标 `FFD` 未达 `NFR-01` 阈值，见 14.3 第一条 —— 功能可用但首字偏慢）
  **仍未闭环**：`RouterOptions.Streaming` 没有实现注入 —— 缺 sherpa online recognizer 封装与 `zipformer-zh-streaming` 模型包，因此真机恒为 `ERR_LOCAL_UNAVAILABLE`，本会话只录音不出实时字（录制不受影响）。见 `DEV-ISSUES-F-live.md` FL-04）
- [x] **录制页**：选源 + 录制控制 + 录音实例信息（已采集 / 预计体积 / 录完再转说明），默认不显示转写流。
- [x] **另存录音文件**：把会话音频另存为单个音频文件带走，导出不改动数据库记录、会话仍可回放。（当前仅 `wav`，FLAC 未实现）

## 5. `FR-01` 模型来源与引擎路由 `[~]`

- [x] **引擎统一接口**：本地与在线实现同一套引擎契约，上层按能力调用而不感知来源差异。
- [x] **本地推理引擎**：接入本地推理运行时（CGO），支持模型档位与线程数配置，完成加载自检与卸载。
- [x] **在线引擎**：支持兼容流式端点、密钥与模型名配置，走代理感知客户端并记录出站。
- [x] **来源切换生效时机**：会话进行中禁止切换，切换在下一个会话生效，避免同一会话内模型混用。
- [x] **降级矩阵**：在线故障可回退本地并标记降级、打点、非阻塞提示；本地故障**不回退**在线，只提示下载或切换来源。
- [x] **引擎预热与热切换**：切换时按需预热目标引擎并给出加载进度，失败回落到可用来源或明确报错。
- [x] **引擎服务与状态事件**：`enginesvc` 暴露切换、健康检查与状态事件，前端能显示当前来源与降级原因。
- [x] **真实推理端到端验证**：用**官方真实权重**跑通离线推理链路（此前只有契约级验证）。（Wave F 实测：SenseVoice int8 239MB + 3D-Speaker 声纹 28MB；中文 5.59s 音频 → `"开饭时间早上9点至下午5点。"`（180ms，语种 `<|zh|>`）、英文 7.15s → 语种 `<|en|>` 且数字后处理正确、声纹 192 维且同段自相似 `1.000000` / 跨段 `0.0466`、首次加载 853ms。过程中发现并修掉两个让真实模型 **100% 失败**的缺陷（`Tokens` 返回裸文件名、官方包被误判为 paraformer），详见 `DEV-ISSUES-F-realmodel.md`。真机入口统一到 `-tags sherpa_models`，默认 `go test ./internal/...` 不编译不联网）

## 10. `NFR-08` 性能预算与自适应限流 `[x]`

- [x] **整机份额口径**：以「整机占用上限减去其他应用占用」计算本应用可用额度，界面文案明确它**不是**本应用上限。（`otherPct = total − self`、`headRoom = N − otherPct`；有单测锁死「4 核占 1 核 ⇒ selfPct = 25 而非 100」的量纲）
- [x] **分平台资源采样**：采样整机与本应用（含推理子进程）的 CPU 占用，采样开销不影响正常使用。（Windows `GetSystemTimes` + `GetProcessTimes` + 进程树枚举、Linux `/proc`；macOS 无免 cgo 采样源，诚实降级为「不采样不降档」）
- [x] **判据与滞回**：用滑动平均而非瞬时值判断，超额持续一段时间才暂停、回落后留滞回带再恢复，避免抖动。（降档确认 3s、升档确认 15s 且额外留 10% 余量、一次只升一级；抖动测试断言档位一动不动）
- [x] **降档阶梯**：额度收窄时先逐级降档（关二次校正 / 降线程 / 跳帧），最低档仍不足才暂停推理。（`perf.ThreadsFor` 给出档位→线程数：L0/L1 = `max(1,cores/2)`、L2 = `max(1,cores/4)`、L3/P = `1`，经 `NewFactoryWithThreads` + `RouterOptions.LoadThreads` 落到 sherpa `NumThreads`，**只在引擎加载时生效**；P 档由 `CheckInferenceAllowed` 在 `Runner.Run` 入口拒绝新任务。两条如实结论：「二次校正」在当前代码不存在（仅边录边转才有），L1 不予伪造第二遍；「跳帧」在整句批量解码的延后转写路径上无对应机制，L2/L3 的实际效果是线程数递减 —— 见 `DEV-ISSUES-E-s8.md` E8-01 / E8-02）
- [x] **录制永不中断**：任何降档与暂停都只影响推理，采集与落盘继续；界面说明暂停原因，避免被读作卡死。（`BudgetState` 无任何停止录制的字段/方法，有反射测试守护；档位变化只叠加 `throttled` / `suspended` 标记）
- [x] **性能打点与事件**：降档、暂停、恢复写入会话时间轴供回放可见，并向前端推送实时用量。（`Recorder.MarkPerf` 写 TBL-10 的 `perf-throttle` / `perf-suspend` / `perf-resume`，`atMs` 用帧计数换算；装配层按「进入暂停 > 恢复 > 降档」优先级判定，附注只写机器可读 token、界面文案由前端 i18n 渲染；EV-15 `perf:usage` 仍 1Hz 推送）
- [x] **设置项与状态反馈**：提供整机性能预算滑杆（默认值与范围按需求文档），设置页展示当前状态、可用额度与占用分量。（API-9.9 校验 10–100 步进 5，返回真实三分量读数；设置页新增性能分区）

### 14.3 非功能验收

- [x] **时延指标**：边录边转路径的首字与持续转写延迟达标记，取样方式按需求文档。（**按 PRD 双指标口径实测 20 次采样（两次独立运行），全部达标**。`FFD-engine`（起点=首个非静音帧，语音起点实测 700ms）P50 **912–913ms** / P95 **915–916ms** vs 阈值 1000/1500 → **达标**；`FFD-e2e`（起点=用户触发，含源音频前导静音，**仅观测不设阈值**）P50 1612–1613ms / P95 1615–1616ms。`SLD` P50 302–303ms / P95 1300–1302ms vs P95≤1500 → **达标**；解码积压 P50 16ms / P95 19–21ms → **达标**（解码比实时快约 6 倍，实现不是瓶颈）。差异 1–3ms 属运行波动，判定余量远大于波动幅度。

  **口径变更（v1.4.0）**：原单指标 `FFD`（起点=用户触发，P50≤900）已废止。它把源音频前导静音计入引擎责任 —— 实测样本静音 700ms 占测量值 43%，指标实际测的是「样本静音多长」而非引擎能力。拆为 `FFD-engine`（约束引擎，P50≤1000）与 `FFD-e2e`（如实呈现用户感知，仅观测）。阈值 1000ms 锚定在「该模型 chunk 结构决定的约 912–922ms 实测下限 + 余量」，不随实测漂移。

  **❗ 必读：本次达标来自口径拆分，不是整体变快。** 若沿用旧的单指标口径（起点=用户触发、含前导静音、阈值 P50≤900），实测 `FFD` 仍为 P50 **1612–1613ms** / P95 **1615–1616ms** —— 即便按新阈值 1000ms 衡量也**依然不达标**，与拆分前相比**没有任何性能改善**。变的只是「把源音频前导静音（实测 700ms）从引擎责任中剥离」，拆出的 `FFD-engine` P50 912–913ms 才落在 1000ms 以内。因此**不要**把本条 `[x]` 读成「首字延迟已优化到 1 秒内」——用户实际感知（从点开始到看见字）仍是约 1.6 秒，这部分由 `FFD-e2e` 如实登记。

  数值口径：上述区间来自**两次独立的 20 次采样**（落地时一次、复核时一次），差异 1–3ms 属正常运行波动（同一二进制、同一音频、同一线程数）；判定余量（引擎指标距 1000ms 阈值约 85ms）远大于波动幅度，结论不因波动改变。`SLD` 与解码积压的阈值与判定未随本次拆分改动。
